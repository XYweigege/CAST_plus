# 需求文档 - 保险客户声音智能分析系统（VoC Insight）

## 1. 项目背景

保险业务的客户声音分散在满意度问卷开放题、索赔结案评价、客服工单、应用商店评论等渠道。这些文本数量大、价值高，但缺乏系统化的分析手段，主要依赖人工抽检，导致三个问题：

1. **主题标签维护滞后**：业务人员手工维护的关键词与分类无法覆盖客户不断变化的口语表达，直接匹配召回率低
2. **高风险反馈发现晚**：涉及拒赔、销售误导的反馈若未及时识别，可能升级为监管投诉
3. **评分无法归因**：只看得到产品满意度分数的涨跌，定位不到具体业务环节

### 1.1 目标用户

| 角色 | 使用场景 |
|------|---------|
| 客户体验负责人 | 查看整体满意度趋势、负面占比、问题主题分布 |
| 索赔部门 | 监控理赔时效、拒赔争议类负面反馈，及时介入个案 |
| 合规部门 | 识别销售误导、监管投诉升级信号 |
| 产品负责人 | 查看某产品线的评分归因报告，定位改进点 |

### 1.2 项目定位

在已有反馈管理机制的基础上做**智能化升级**，而非从零新建系统。原有的人工维护能力保留，AI 负责穷举与初筛，人负责确认与把关。

## 3. 非功能需求

### 3.1 性能

- 页面首屏加载 < 3s
- 分页查询响应 < 500ms
- 单条 AI 标注 < 5s（受模型影响）
- 批量分析并发控制在 3 以内，避免触发限流

### 3.2 可用性

- AI 服务不可用时流程不中断，降级为规则兜底
- 单条反馈处理失败不影响整批流程
- 主题词扩展结果缓存，避免重复调用

### 3.3 安全与合规

- API Key 仅存于服务端环境变量，不下发前端
- 客户原始数据出境前须脱敏（香港《个人资料（私隐）条例》）
- AI 输出仅供参考，不构成业务或合规结论，界面需明示
- 生产环境需补充鉴权与部门级数据隔离

## 4. 数据规格

### 4.1 反馈渠道

| 编码 | 渠道 | 说明 |
|------|------|------|
| survey | 客户问卷 | NPS / CSAT 开放题 |
| claim | 索赔反馈 | 结案后评价 |
| service | 客服工单 | 会话与工单记录 |
| social | 社媒公开 | 公开渠道内容 |
| appstore | 应用商店 | App 评分评论 |
| email | 客户邮件 | 邮件往来 |

### 4.2 产品线

| 编码 | 产品线 |
|------|--------|
| travel | 旅行保险 |
| medical | 医疗保险 |
| accident | 个人意外险 |
| home | 家居保险 |
| motor | 汽车保险 |
| pet | 宠物保险 |

### 4.3 主题标签体系

理赔时效、赔付金额争议、拒赔争议、核保与投保、客服响应、服务态度、条款清晰度、销售误导、续保与退保、APP 与网站体验、价格与性价比、理赔资料繁琐。

主题体系是整个分析层的骨架，Prompt 约束、前端筛选、归因报告共用同一套枚举。新增主题需同步更新 `server/src/constants.ts` 与 `client/src/constants.ts`。

### 4.4 紧急度分级标准

| 级别 | 判定标准 |
|------|---------|
| critical | 涉及拒赔、销售误导、威胁投诉至监管机构、扬言退保并公开曝光 |
| action | 明确要求跟进、投诉、索赔受阻、多次催促未果 |
| attention | 有明确不满但无升级诉求 |
| info | 一般咨询、中性描述、正面反馈 |

## 5. AI 分析规格

### 5.1 标注 Prompt 设计要点

1. **限定输出空间**：主题必须从给定列表中选，避免标签爆炸
2. **显式列出方言特征**：粤语负面表达（`唔賠`/`搵笨`/`搞咁耐`）需显式告知模型
3. **Few-shot 示例**：覆盖繁中、粤语、英文、混排四类形态各至少一例
4. **低温度**：标注任务要求一致性，`temperature=0.1`
5. **置信度自评**：让模型输出 confidence，为人工复核提供路由依据

### 5.2 模型选择

默认 `deepseek/deepseek-v3.2`，通过 `AI_MODEL` 环境变量可覆盖。更换模型时应重跑评测集对比。

### 5.3 质量评估

评测集位于 `server/src/__tests__/aiRelevance.test.ts`，12 条标注用例覆盖四类语言形态。

质量底线：情感倾向准确率 ≥ 80%，主题归类命中率 ≥ 80%。紧急度允许 ±1 级容差。

## 6. 接口设计

### 6.1 RESTful API

```
# 主题词
GET    /api/topics                 主题词列表
POST   /api/topics                 创建主题词
PUT    /api/topics/:id             更新
DELETE /api/topics/:id             删除
PATCH  /api/topics/:id/toggle      启停
POST   /api/topics/:id/expand      AI 扩展口语变体
PATCH  /api/topics/:id/approve     人工确认 / 否决

# 客户反馈
GET    /api/feedbacks              列表（支持渠道/情感/紧急度/产品线/主题/时间/待复核筛选）
GET    /api/feedbacks/stats        概览统计
GET    /api/feedbacks/insight      评分归因报告（?productLine=）
GET    /api/feedbacks/:id          详情
POST   /api/feedbacks/analyze      单条即时分析（不落库）
POST   /api/feedbacks/import       CSV / JSON 导入
POST   /api/feedbacks/generate-demo 生成演示数据
PATCH  /api/feedbacks/:id/review   人工复核
DELETE /api/feedbacks/:id          删除

# 预警
GET    /api/alerts                 预警列表
PATCH  /api/alerts/:id/read        标记已读
PATCH  /api/alerts/read-all        全部已读
PATCH  /api/alerts/:id/handle      标记处置
DELETE /api/alerts/:id             删除

# 其他
POST   /api/check-feedbacks        手动触发一轮分析
GET    /api/health                 健康检查
```

### 6.2 WebSocket 事件

```
# 服务端 → 客户端
feedback:new   新反馈入库
alert          新预警产生

# 客户端 → 服务端
subscribe      订阅主题词频道
unsubscribe    取消订阅
```
