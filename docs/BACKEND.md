## 第一章 架构总览

### 1.1 分层结构

```
┌─────────────────────────────────────────────┐
│ 表现层  index.ts                             │
│         Express 路由注册 · Socket.io · cron  │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────┴──────────────────────────┐
│ 接口层  routes/                              │
│   topics · feedbacks · alerts · settings     │
│   职责：参数校验 · 组装查询 · 组装响应        │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────┴──────────────────────────┐
│ 业务层  jobs/insightRunner.ts                │
│   分析主流程编排（唯一的核心流程）            │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────┴──────────────────────────┐
│ 能力层  services/                            │
│   ai.ts           LLM 标注 / 扩展 / 归因     │
│   feedbackSource.ts  语料生成 / 文件解析     │
│   email.ts        预警邮件 / 日报            │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────┴──────────────────────────┐
│ 数据层  prisma/schema.prisma · db.ts         │
│   SQLite + Prisma ORM                        │
└─────────────────────────────────────────────┘
```

**分层的意义**：路由层不写业务逻辑，只做参数处理；业务流程集中在 `insightRunner`；
AI 调用、邮件、数据源各自独立。这样替换任意一层（比如换数据源、换模型）都只影响一个文件。

### 1.2 一个请求的完整流转

以「前端加载反馈列表」为例：

```
GET /api/feedbacks?sentiment=negative&urgency=critical&sortBy=urgency&page=1&limit=20
  ↓
index.ts          路由分发到 feedbacksRouter
  ↓
routes/feedbacks.ts
  ├─ 解析 query 参数 → 组装 Prisma where 条件
  ├─ 判断是否需要内存排序（urgency 需要）
  ├─ prisma.feedback.findMany() + count()  并行查询
  └─ 内存排序 → 分页切片 → 返回 { data, pagination }
  ↓
前端渲染表格
```

以「定时分析任务」为例：

```
cron 触发 runInsightCheck()
  ↓
拉取激活主题词 → 采集反馈
  ↓
对每个主题词：扩展 → 预匹配 → AI 标注 → 落库 → 命中计数 → 推送/预警
  ↓
突增检测
```

### 1.3 技术选型与理由

| 技术 | 用途 | 为什么选 |
|------|------|---------|
| Express 5 | HTTP 服务 | 轻量，路由与中间件模型足够 |
| Prisma 6 | ORM | 类型安全，模型变更自动同步到 TS 类型 |
| SQLite | 数据库 | 零部署成本，适合原型；生产可换 PostgreSQL |
| Socket.io | 实时推送 | 自动降级（WebSocket → 轮询），断线重连 |
| node-cron | 定时任务 | 表达式灵活，频率可通过环境变量配置 |
| OpenRouter | LLM 网关 | 一个 Key 访问多家模型，便于横向对比与切换 |
| Vitest | 测试 | 与 Vite 生态一致，启动快 |

**为什么用 OpenRouter 而不是直接调某家 API**：这个项目需要对比不同模型在
粤语/繁中标注任务上的表现。用网关可以在不改代码的前提下换模型
（`AI_MODEL` 环境变量），评测集跑一遍就能横向对比。

## 第二章 数据模型

### 2.1 总览

```
Topic（主题词） 1 ──── N  Feedback（客户反馈）
                              │
Alert（预警）  N ───── 1 ─────┘（软关联，feedbackId 非外键）
```

`Alert` 与 `Feedback` 是**软关联**——`feedbackId` 只是普通字段，没有外键约束。
这是有意的：突增预警（`type: 'surge'`）不对应单条反馈，加外键会限制这种场景。

### 2.2 Topic（主题词）

```prisma
model Topic {
  id            String   @id @default(uuid())
  text          String   @unique
  category      String?
  isActive      Boolean  @default(true)
  hitCount      Int      @default(0)      // 命中次数
  autoGenerated Boolean  @default(false)  // 是否 AI 生成
  approved      Boolean  @default(true)   // 人工确认状态
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt
  feedbacks     Feedback[]
}
```

**三个新增字段构成调优闭环**：

| 字段 | 作用 |
|------|------|
| `autoGenerated` | 区分人工维护与 AI 生成，前端展示不同来源标签 |
| `approved` | AI 生成的变体默认 `false`，需人工确认才启用 |
| `hitCount` | 累计命中次数，零命中的变体可被淘汰 |

闭环：

```
人工录入主题词 → AI 扩展变体(approved=false, isActive=false)
  → 人工确认(approved=true, isActive=true)
  → 参与匹配，累计 hitCount
  → 依据 hitCount 淘汰低效词
```

**为什么 AI 生成的变体默认不启用**：模型会生成一些看似合理但实际不会出现的表达
（比如过于书面化或生造的说法）。让它们直接进入生产会污染匹配结果。
默认关闭、人工确认，是**让模型负责穷举、人负责把关**。

### 2.3 Feedback（客户反馈）

字段分四组理解：

**① 原始信息（采集得到）**

| 字段 | 说明 |
|------|------|
| `content` | 反馈正文 |
| `source` | 渠道编码 |
| `sourceId` | 业务系统内唯一 ID，**去重的依据** |
| `rating` | 客户评分 1-5 |
| `productLine` | 产品线编码 |
| `language` | `zh-HK` / `en` / `mixed` |
| `authorName` | 客户名（应当脱敏） |
| `publishedAt` | 反馈发生时间 |

**② AI 分析输出**

| 字段 | 说明 |
|------|------|
| `sentiment` | 情感：positive / neutral / negative |
| `topics` | 主题标签，JSON 数组字符串 |
| `urgency` | 紧急度：info / attention / action / critical |
| `urgencyReason` | 定级理由 |
| `aiSummary` | 归因（不是摘要，是"哪个环节出了问题"） |
| `confidence` | 置信度 0-1 |

**③ 人工复核**

| 字段 | 说明 |
|------|------|
| `humanLabel` | 人工修正结果 JSON |
| `isReviewed` | 是否已复核 |

**④ 关联**

`topicId` → 归属哪个主题词命中

**索引设计**

```prisma
@@unique([source, sourceId])
@@index([createdAt])
@@index([urgency])
@@index([sentiment])
```

`@@unique([source, sourceId])` 是去重的核心。注意 SQLite 中 NULL 不参与唯一性判断，
所以 `sourceId` 为空的记录可以有多条（不会互相冲突），这是合理的行为。

### 2.4 已知技术债：`topics` 用 JSON 字符串存

```prisma
topics String?  // '["理赔时效","客服响应"]'
```

**带来的限制**：查询只能走 `contains` 模糊匹配。

```typescript
if (topic) where.topics = { contains: String(topic) };
```

这在数据量大时有两个问题：无法走索引、可能误匹配（"理赔时效"会匹配到"理赔时效性"）。

**正确做法**是建 `FeedbackTopic` 关联表。当前选择 JSON 是为了控制改造规模，
属于有意妥协，已在 README 中标注为生产落地前需改造项。

如果面试被问到，直接承认并说明权衡——**能说清取舍比假装完美更有说服力**。

## 第三章 接口设计

### 3.1 设计约定

| 约定 | 说明 |
|------|------|
| 路径前缀 | 统一 `/api` |
| 资源复数 | `/topics` `/feedbacks` `/alerts` |
| 分页 | `page` + `limit`，返回 `{ data, pagination }` |
| 排序 | `sortBy` + `sortOrder` |
| 时间筛选 | `timeRange`（24h/today/7d/30d）或 `timeFrom`/`timeTo` |
| 空值参数 | 空字符串视为"不筛选"，前端不传该参数 |

**路由顺序的坑**：`/stats`、`/insight`、`/analyze` 必须声明在 `/:id` 之前，
否则会被 `/:id` 捕获（Express 按声明顺序匹配）。当前代码已遵循。

### 3.2 主题词接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/topics` | 列表，按命中次数降序 |
| GET | `/api/topics/:id` | 详情（含最近 20 条反馈） |
| POST | `/api/topics` | 创建 |
| PUT | `/api/topics/:id` | 更新 |
| DELETE | `/api/topics/:id` | 删除 |
| PATCH | `/api/topics/:id/toggle` | 启停 |
| POST | `/api/topics/:id/expand` | **AI 扩展口语变体** |
| PATCH | `/api/topics/:id/approve` | **人工确认/否决** |

**`expand` 接口的实现要点**：

```typescript
const variants = await expandTopic(topic.text);
const existing = await prisma.topic.findMany({ select: { text: true } });
const existingSet = new Set(existing.map(t => t.text));

for (const v of variants) {
  if (v === topic.text || existingSet.has(v)) continue;
  await prisma.topic.create({
    data: {
      text: v,
      category: topic.category,
      autoGenerated: true,
      approved: false,
      isActive: false          // 关键：未确认前不参与监控
    }
  });
}
```

三个细节：

1. **先查已有词表再插入**——避免重复。虽然 `text` 有唯一约束会报错，
   但用 try/catch 兜错误不如提前过滤清晰。
2. **`isActive: false`**——这是"人工确认"机制的落点。
3. **`category` 继承父主题词**——扩展变体与原词同属一个类别，便于分组。

### 3.3 反馈接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/feedbacks` | 列表（多维筛选 + 排序 + 分页） |
| GET | `/api/feedbacks/stats` | 概览统计 |
| GET | `/api/feedbacks/insight` | 评分归因报告 |
| GET | `/api/feedbacks/:id` | 详情 |
| POST | `/api/feedbacks/analyze` | 单条即时分析（不落库） |
| POST | `/api/feedbacks/import` | CSV/JSON 导入 |
| POST | `/api/feedbacks/generate-demo` | 生成演示数据 |
| PATCH | `/api/feedbacks/:id/review` | 人工复核 |
| DELETE | `/api/feedbacks/:id` | 删除 |

**列表接口支持的筛选参数**：

```
source  sentiment  urgency  productLine  topicId
keyword  pendingReview  timeRange / timeFrom+timeTo
sortBy(createdAt|urgency|rating|confidence|publishedAt)  sortOrder
```

**内存排序的处理**（值得单独讲）：

```typescript
const needsMemorySort = sortBy === 'urgency';
let orderBy: any = { createdAt: sortOrder === 'asc' ? 'asc' : 'desc' };
if (!needsMemorySort) { /* 设置其他 orderBy */ }

const [rows, total] = await Promise.all([
  prisma.feedback.findMany({
    where,
    orderBy,
    ...(needsMemorySort ? {} : { skip, take: limitNum })   // 需要内存排序时先全量取
  }),
  prisma.feedback.count({ where })
]);

if (needsMemorySort) {
  const sorted = sortFeedbacks(rows, 'urgency', sortOrder);
  data = sorted.slice(skip, skip + limitNum);
}
```

**为什么 `urgency` 不能直接用 Prisma 排序**：紧急度的业务顺序是
`critical < action < attention < info`（数值越小越紧急），
而字典序是 `action < attention < critical < info`，完全不同。
Prisma 不支持自定义排序规则，只能全量取出后在内存排。

**这个方案的代价**：数据量大时全量取会有性能问题。
生产环境应在数据库层存储一个 `urgencyOrder` 数值字段，直接 `orderBy`。

**`analyze` 接口的价值**：不落库，纯粹用于调试 Prompt。
改完 Prompt 立刻粘几条文本看效果，比跑批量快得多。这是给开发留的调试入口。

**`review` 接口**（人机协同的落点）：

```typescript
await prisma.feedback.update({
  where: { id },
  data: {
    humanLabel: JSON.stringify({ sentiment, topics, urgency }),
    ...(sentiment && { sentiment }),
    ...(topics && { topics: JSON.stringify(topics) }),
    ...(urgency && { urgency }),
    isReviewed: true,
    confidence: 1        // 人工确认即为终态
  }
});
```

`confidence: 1` 的语义是"这是人工确认的结果，不再需要复核"。
`humanLabel` 保留了完整的修正记录，可用于后续分析模型的错误模式。

### 3.4 预警接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/alerts` | 列表（unreadOnly / unhandledOnly） |
| PATCH | `/api/alerts/:id/read` | 标记已读 |
| PATCH | `/api/alerts/read-all` | 全部已读 |
| PATCH | `/api/alerts/:id/handle` | **标记业务已处置** |
| DELETE | `/api/alerts/:id` | 删除 |
| DELETE | `/api/alerts` | 清空 |

**`isRead` 与 `handled` 两个状态位的区别**：

- `isRead`：看到了
- `handled`：处理完了

这是两级状态，符合实际工作流——看到不代表处理完。
统计接口里的 `pendingAlert` 用的是 `handled: false`，即**真正未处置的数量**。

如果只有一个 `isRead`，统计数据会失真（已读未处理的被算作已处理）。

### 3.5 其他

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/health` | 健康检查 |
| POST | `/api/check-feedbacks` | 手动触发一轮分析 |
| GET/PUT | `/api/settings` | 键值配置（保留自原项目） |

## 第四章 核心流程 insightRunner

这是后端唯一的业务流程编排文件，也是整个系统的心脏。

### 4.1 完整流程

```
runInsightCheck()
│
├─ 1. 拉取所有 isActive 的主题词
│     若无 → 直接返回（没有监控目标就不空跑）
│
├─ 2. fetchNewFeedback()  采集一批反馈
│
├─ 3. 对每个主题词：
│   │
│   ├─ 3.1 expandTopic()       主题词 → 客户口语变体
│   │
│   └─ 3.2 对每条反馈：
│       ├─ 去重检查（source + sourceId）
│       ├─ 预匹配（未命中则跳过，省 AI 调用）
│       ├─ analyzeFeedback()   AI 六元组标注
│       ├─ 归属判断（命中扩展词 或 AI 主题匹配）
│       ├─ 落库
│       ├─ 主题命中次数 +1
│       ├─ Socket.io 推送
│       └─ 若 urgency ∈ [action, critical]：
│           ├─ 创建 Alert
│           ├─ 推送 alert 事件
│           └─ 发送邮件
│
└─ 4. detectSurge()  主题突增检测
```

### 4.2 逐步代码解读

**① 主题词扩展**

```typescript
const expanded = await expandTopic(topic.text);
```

有缓存（`Map`），同一主题词不会重复调用 AI。
这一句把"理赔时效"变成 `["理赔时效","理赔慢","拖咗好耐都未批","幾時先賠到",...]`。

**② 去重**

```typescript
const existing = await prisma.feedback.findFirst({
  where: { source: item.source, sourceId: item.sourceId ?? null }
});
if (existing) continue;
```

注意这里是 `findFirst` 查询而不是依赖数据库唯一约束抛错——因为外层有 try/catch，
用查询判断更清晰，且能明确区分"重复"和"出错"。

**③ 预匹配（成本优化的关键）**

```typescript
const preMatch = preMatchTopic(item.content, expanded);
```

**为什么需要这一步**：AI 调用是成本和延迟的主要来源。
先用扩展词做字符串匹配，未命中的反馈不送 AI。
这一步能过滤掉大部分无关反馈，直接决定了系统的运行成本。

**④ AI 分析**

```typescript
const analysis = await analyzeFeedback(item, preMatch);
```

`preMatch` 传入 Prompt，作为给模型的提示（"文本中命中了这些变体"）。

**⑤ 归属判断**

```typescript
const topicMatched =
  preMatch.matched ||
  analysis.topics.some(t =>
    t === topic.text || topic.text.includes(t) || t.includes(topic.text)
  );
if (!topicMatched) continue;
```

两个条件任一成立即归入该主题：

- 文本命中了扩展词（字面匹配）
- AI 判定的主题与当前主题词相关（语义匹配）

**为什么需要语义兜底**：客户可能完全不提"理赔时效"这四个字，
但说的是"等咗兩個星期都未批"——字面匹配不到，但 AI 能判定主题是"理赔时效"。
两条路径互补，提高召回。

**⑥ 命中计数**

```typescript
await prisma.topic.update({
  where: { id: topic.id },
  data: { hitCount: { increment: 1 } }
});
```

这个简单的自增是调优闭环的数据基础。没有它，就无法判断哪些变体有效。

**⑦ 预警节流**

```typescript
if (ALERT_URGENCIES.includes(analysis.urgency)) {  // 仅 action / critical
```

**只有两级触发预警**。如果 `attention` 也告警，一个中等规模的系统每天会产生
几十条预警，业务方很快就会忽略所有告警——这就是**告警疲劳**。
宁可漏掉一些低优先级的，也要保证高优先级预警被看到。

### 4.3 突增检测算法

```typescript
const SURGE_THRESHOLD = 5;        // 24h 内同主题负面反馈数阈值
const SURGE_COOLDOWN_HOURS = 12;  // 静默期
```

流程：

```
1. 查询 24h 内所有 sentiment=negative 的反馈
2. 解析每条的 topics，统计各主题出现次数
3. 对超过阈值且在 TOPIC_TAGS 内的主题：
   a. 检查静默期：12h 内是否已有同主题的 surge 预警 → 有则跳过
   b. 创建 surge 预警并推送
```

**为什么需要这个功能**：单条反馈看不出系统性问题。
一条"理赔慢"是偶发，20 条"理赔慢"是流程出事了。
突增检测把"个体信号"聚合成"系统信号"，这是它相对普通列表的价值。

**静默期的必要性**：定时任务每 30 分钟跑一次，
同一个突增如果不加静默期，一天会产生 48 条相同预警。

**当前实现的局限**（面试可以说）：阈值是固定的绝对值（5 条），
没有考虑基线——如果某日常负面反馈是 50 条，5 条根本不算突增。
生产环境应该用**相对基线的统计方法**（如与过去 30 天同主题日均值的标准差比较）。

## 第五章 AI 层（services/ai.ts）

这是技术含量最高的文件。逐个函数拆解。

### 5.1 `isAIConfigured()`：降级的开关

```typescript
function isAIConfigured(): boolean {
  const key = process.env.OPENROUTER_API_KEY ?? '';
  return key.length > 0 && !key.startsWith('your_');
}
```

**为什么不能直接判断非空**：`.env.example` 里的占位符 `your_openrouter_api_key_here`
也是非空。只判断非空会导致每次都发出必然失败的请求，再走兜底，
白白增加延迟并刷一堆 401 错误日志。

这个细节看起来小，但它决定了**没配 Key 时系统能不能正常演示**。

### 5.2 `expandTopic()`：书面术语 → 客户口语

**解决的问题**：业务人员维护"理赔时效"，客户说"拖咗好耐都未賠"。
直接字符串匹配召回率极低。

**Prompt 关键约束**：

```
规则：
1. 必须覆盖香港客户的常用表达，包含繁体中文、粤语口语、英文及中英混排
2. 包含书面说法与缩写
3. 不要加入与主题无关的泛化词（如"保险""服务"这种任何主题都会出现的词）
4. 总数控制在 6-15 个
```

第 3 条尤其重要——如果生成"保险""服务"这类词，几乎每条反馈都会命中，
匹配就失去了区分度。

**参数**：`temperature: 0.2`（略高于标注任务的 0.1，因为扩展需要一点多样性）、
`maxTokens: 400`。

**缓存**：`Map<string, string[]>`，同一主题词只调用一次。

**兜底**：`extractCoreTerms()` 纯文本拆分作为最终兜底，保证任何情况下都有返回值。

### 5.3 `preMatchTopic()`：预匹配

```typescript
export function preMatchTopic(text: string, expandedTopics: string[]) {
  const lowerText = text.toLowerCase();
  const matchedTerms: string[] = [];
  for (const kw of expandedTopics) {
    if (lowerText.includes(kw.toLowerCase())) matchedTerms.push(kw);
  }
  return { matched: matchedTerms.length > 0, matchedTerms };
}
```

简单的包含匹配，不区分大小写。返回 `matchedTerms` 是为了传给 Prompt
作为提示信息（"文本中命中了这些变体"），提升模型判断准确率。

### 5.4 `analyzeFeedback()`：六元组标注

#### Prompt 逐段解读

**① 角色与任务定义**

```
你是保险行业客户体验分析专家，负责把客户反馈结构化为可行动的分析结果。
```

"可行动"三个字是核心——不是让模型描述内容，而是输出能驱动业务动作的结果。

**② 主题标签硬约束**

```
【可选主题标签】${TOPIC_TAGS.join('、')}
2. topics：从【可选主题标签】中选择 1-3 个，**不要自造标签**
```

不加这条，模型会输出"理赔问题""效率低下"这类自由文本。
一段时间后标签数量爆炸，报表没法看。

**③ 紧急度四级定义（带具体判定标准）**

```
- critical：涉及拒赔、销售误导、威胁投诉至监管机构（如 IA / 保险投诉局）、扬言退保并公开曝光
- action：明确要求跟进、投诉、索赔受阻、多次催促未果
- attention：有明确不满但无升级诉求
- info：一般咨询、中性描述、或正面反馈
```

**关键**：每一级都给了具体的语义特征，而不只是抽象描述。
特别是 `critical` 列举了"威胁投诉至监管机构"——这是保险场景特有的高风险信号，
通用模型不会知道。

**④ 语言适配**

```
【语言注意】
客户可能使用繁体中文、粤语口语或中英混排。以下均为强负面表达：
"唔賠""搵笨""搞咁耐""拖咗好耐""極不負責任""講一套做一套""no response""waste of time"
```

通用情感模型多在简体中文或英文语料上训练，对粤语口语识别率低。
显式列出是最低成本的领域适配手段。

**⑤ Few-shot 示例（三条，覆盖典型场景）**

```
输入：「理賠拖咗兩個星期都未批...」→ 粤语负面，attention
输入：「Claim was rejected... escalate to the Insurance Authority.」→ 英文拒赔，critical
输入：「客服阿 May 解釋得好清楚...」→ 繁体正面，info
```

三条分别覆盖：粤语负面、英文高风险、繁体正面。
**示例比规则描述更有效**，尤其是 `aiSummary` 的写法——模型通过示例才理解
"归因"和"摘要"的区别。

**⑥ 输出格式约束**

```
只输出 JSON，不要有其他内容。
{"sentiment":"","topics":[],"urgency":"","urgencyReason":"","aiSummary":"","confidence":0}
```

给出空模板，进一步约束输出结构。

#### 调用参数

```typescript
temperature: 0.1,   // 标注任务要一致性
maxTokens: 500,
```

`temperature: 0.1` 是刻意的。标注任务要的是**同一条文本多次分析结果一致**，
高温会导致结果漂移，评测准确率也会剧烈波动。

#### 输出校验（三重防线）

```typescript
// 1. 正则提取 JSON
const jsonMatch = responseContent.match(/\{[\s\S]*\}/);

// 2. 主题标签白名单过滤
const topics = Array.isArray(parsed.topics)
  ? parsed.topics.filter(t => typeof t === 'string' && TOPIC_TAGS.includes(t))
  : [];

// 3. 枚举值校验 + 默认值
sentiment: (['positive','neutral','negative'].includes(parsed.sentiment) ? parsed.sentiment : 'neutral'),
urgency:   (['info','attention','action','critical'].includes(parsed.urgency) ? parsed.urgency : 'info'),
confidence: Math.min(1, Math.max(0, Number(parsed.confidence) || 0.5))
```

**为什么需要三重**：Prompt 约束是第一道，但模型不保证遵守。
`confidence` 的 `Math.min/max` 钳制防止模型输出 1.5 或 -0.3 这类值污染数据。

#### 兜底策略

```typescript
function fallbackAnalysis(item, preMatch) {
  const negativeHints = ['唔賠','搵笨','失望','投訴','拖','慢','差','reject','delay','slow','bad','worst'];
  const isNegative = hit.length > 0 || (item.rating != null && item.rating <= 2);
  return {
    sentiment: isNegative ? 'negative' : 'neutral',
    topics: [],
    urgency: isNegative ? 'attention' : 'info',
    confidence: 0.3     // 低置信度 → 自动进入待复核队列
  };
}
```

兜底只做**负面识别**，不做正面识别。这是保守策略：
宁可把正面判成中性（无害），也不要把负面判成中性（漏掉风险）。

`confidence: 0.3` 会自动进入待复核队列——兜底结果也标记了不确定性。

### 5.5 `generateInsightReport()`：统计与归纳分离

这是设计上最值得讲的一处。

**第一部分：代码计算（确定性）**

```typescript
const totalFeedback = rows.length;
const avgRating = /* 均值计算 */;
const negativeRatio = /* 负面占比 */;
const topTopics = /* 主题分布统计 */;
```

**第二部分：LLM 归纳（语义）**

```typescript
const sampleSummaries = rows
  .filter(r => r.sentiment === 'negative')
  .slice(0, 30)                    // 只取前 30 条负面摘要
  .map((r, i) => `${i + 1}. ${r.aiSummary || r.content.slice(0, 80)}`)
  .join('\n');
```

**为什么这么分**：

> 计数是 LLM 的弱项，容易编造数字。反馈量、评分均值、主题分布这些必须
> 可复现、可对账，交给代码；"为什么评分低""怎么改进"是语义任务，交给模型。
> 各用所长。

**只取 30 条负面摘要**是 token 成本控制——不需要把 300 条全塞进去，
30 条足以让模型归纳出主要问题。

**Prompt 的约束**：

```
1. summary：3 句话以内，说明该产品线客户体验的整体状况与主要失分点，要有观点不要罗列
2. suggestions：3 条具体的改进建议，每条要指向明确的业务环节，可执行，不要空话
```

"要有观点不要罗列""不要空话"——这类否定式约束对提升输出质量很有效，
否则模型会输出"加强沟通、优化流程"这类废话。

**语言自动识别**：

```typescript
function detectLanguage(text: string): string {
  const hasCJK = /[\u4e00-\u9fff]/.test(text);
  const hasLatin = /[a-zA-Z]{3,}/.test(text);
  if (hasCJK && hasLatin) return 'mixed';
  if (hasCJK) return 'zh-HK';
  return 'en';
}
```

**评分与情感一致性**：

```typescript
function ratingBySentiment(sentiment: Sentiment): number {
  if (sentiment === 'negative') return 1 + Math.floor(Math.random() * 2);  // 1-2
  if (sentiment === 'positive') return 4 + Math.floor(Math.random() * 2);  // 4-5
  return 3;                                                                 // 中性
}
```

保证生成的评分与情感标注不矛盾——如果负面反馈给 5 分，数据就不可信了。

### 6.2 文件导入解析

支持 JSON 与 CSV 两种格式。

**JSON 的容错设计**：

```typescript
const parsed: unknown = JSON.parse(raw);
const list: Record<string, unknown>[] = Array.isArray(parsed)
  ? (parsed as Record<string, unknown>[])
  : ((parsed as { data?: Record<string, unknown>[] })?.data ?? []);
```

同时支持裸数组和 `{ data: [...] }` 包装。

**类型标注的必要性**：`JSON.parse` 返回 `any`，

会是隐式 `any`，触发 TS7006。这是实际踩过的坑（见 DEVELOPMENT.md 附录 A3）。

**CSV 的字段容错**：

```typescript
const contentIdx = headers.indexOf('content') >= 0
  ? headers.indexOf('content')
  : headers.indexOf('text');   // 兼容 text 作为正文字段名
```

## 第八章 工程细节

### 8.1 前后端共用的排序逻辑

`server/src/utils/sortFeedbacks.ts` 与 `client/src/utils/sortFeedbacks.ts` 逻辑完全一致。

**为什么需要两份**：后端用于内存排序（urgency），前端用于本地排序。
两份保持一致才能保证"切换排序方式后，前端显示顺序与后端一致"。

**代价**：需要同步维护两份。这是为了保持前后端独立部署能力做的妥协。

**`urgency` 排序的特殊处理**：

```typescript
case 'urgency': {
  result = compareUrgency(a, b);
  if (result === 0) {
    // 相同紧急度按创建时间兜底
    result = toTimestamp(a.createdAt) - toTimestamp(b.createdAt);
    return desc ? -(result) : result;
  }
  // URGENCY_ORDER 中 critical=0 最小，
  // desc（最紧急在前）直接返回 result
  return desc ? result : -result;
}
```

这段逻辑不容易一眼看懂。`URGENCY_ORDER` 中 `critical: 0` 最小，
所以 `result < 0` 意味着 a 更紧急。desc 时希望 a 在前 → 直接返回 `result`。
注释里写明了推导过程，避免后人改错。

### 8.2 错误处理策略

三层：

| 层级 | 策略 |
|------|------|
| 单条反馈处理 | try/catch 包裹，失败只跳过该条，不影响整批 |
| 单个主题词处理 | try/catch 包裹，失败只跳过该主题词 |
| AI 调用 | 失败走规则兜底，返回可用结果 |

**核心原则**：批量处理时，单条失败不应中断整批。
这条原则在反馈处理循环中体现得很明确。
