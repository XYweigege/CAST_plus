## 零、改造策略：为什么是"改造"而不是"重写"

这是整个改造的第一个、也是最重要的决策。

**判断依据**：原项目（Express + Prisma + React + Socket.io + OpenRouter）的技术骨架和工程实践
（限流、去重、缓存、错误兜底、前后端共用排序逻辑）与业务场景无关，属于可复用资产。
真正与"热点监控"绑定的只有：数据模型字段、AI Prompt、爬虫数据源三处。

**结论**：

| 维度 | 决策 | 理由 |
|------|------|------|
| 技术架构 | **保留** | 与业务无关，重写是重复劳动 |
| 工程实践 | **保留** | 限流/去重/兜底这些细节，重写容易漏 |
| 业务语义 | **全换** | 数据模型、Prompt、UI 文案、数据源 |
| 项目身份 | **重建** | 见下 |

**关于项目身份**：原项目是公开的教学项目，使用者基数大。直接把它当简历项目提交，
有被面试官认出是"跟着教程做的"的风险。因此：
**代码照搬架构，但项目名、README、所有业务语义全部重建，代码里不留原项目的痕迹。**

一句话总结策略：**改代码，换身份。**

## 一、摸底：先搞清楚原项目是什么

动手前先通读了这些文件：

| 文件 | 从中得到的信息 |
|------|--------------|
| `README.md` / `docs/REQUIREMENTS.md` | 原项目定位、功能清单、接口设计 |
| `prisma/schema.prisma` | 数据模型：`Keyword` / `Hotspot` / `Notification` / `Setting` |
| `services/ai.ts` | AI 层三件事：查询扩展、内容分析、批量分析 |
| `jobs/hotspotChecker.ts` | 主流程：拉关键词 → 多源抓取 → 去重 → 过滤 → AI 分析 → 落库 → 推送 |
| `routes/*.ts` | 接口设计与筛选参数 |
| `App.tsx` / `services/api.ts` | 前端结构与前后端契约 |

**关键发现**：这个项目的本质不是"热点监控"，而是一个通用的**情报监控引擎**：

```
关键词订阅 → 多源采集 → AI 相关性判定 → 分级 → 实时推送
```

热点只是它落在 AI 圈的一个垂直场景。这个发现决定了整个改造的可行性——
只要替换"AI 相关性判定"这一步的语义，整套管线就能复用到任何监控/分析场景。

## 二、定方向：保险领域做什么业务

### 候选方向对比

| 方向 | 数据源 | 技术深度 | 差异化 | 数据门槛 |
|------|--------|---------|--------|---------|
| 监管政策合规 | 金监总局、央行、协会 | 中 | 高 | 无 |
| 保险舆情 | 社媒、投诉平台 | 中 | 低（红海） | 无 |
| 竞品动态 | 产品条款、费率披露 | 中 | 中 | 无 |
| 灾害理赔预警 | 气象、地震台网 | 高 | 高 | **需要保单数据** |

### 决策过程

1. 最初倾向监管政策（刚需、数据源公开）
2. 用户提到做过灾害理赔预警（OneClaim）→ 一度倾向灾害方向
3. **关键转折**：用户说明真实背景——保险公司子公司，做的是**产品评分、评论、关键词管理系统**，且有客户调查问卷数据

第 3 条信息让结论翻转：

> 外部舆情本质上是"偷听"——因为听不到客户真实声音，才去社媒上猜。
> 但业务方**已经有客户主动提供的声音**（问卷开放题、索赔反馈）。

| | 外部舆情 | 内部客户声音 |
|---|---|---|
| 数据质量 | 噪音大、样本偏（只有爱抱怨的人才公开说） | 结构化、可回溯到具体客户 |
| 可行动性 | "有人说 XX 垃圾" → 无从下手 | "索赔时效不满" → 可直接改流程 |
| 壁垒 | 竞品也能买同样的服务 | **只有你有** |

**最终定位**：以内部客户声音（VoC）为核心，不做纯外部舆情。
改造成本也最低——原项目的多源采集能力正好用于汇聚 6 类反馈渠道。

## 三、数据模型：为什么从最底层开始

**为什么第一步改 schema**：数据模型是所有代码的类型来源（Prisma Client 自动生成类型）。
模型定错，上层所有代码都要跟着改，返工成本最高。它是"上游"，必须先定。

### 字段改造思路

原 `Hotspot` 的字段是为社媒设计的（`viewCount` / `retweetCount` / `danmakuCount`），
在保险反馈场景完全无意义。改造分三类：

| 类别 | 处理 | 示例 |
|------|------|------|
| 与场景绑定且无用 | **删除** | `retweetCount`、`danmakuCount`、`authorAvatar` |
| 通用但需更名 | **改名 + 调语义** | `relevance` → 拆分；`importance` → `urgency` |
| 场景需要但没有 | **新增** | `sentiment`、`topics`、`confidence`、`isReviewed` |

### 三个关键字段的设计意图

**`confidence`（置信度）**

这个字段是整个"人机协同"设计的支点。AI 输出置信度，低于 0.7 的判定
`isReviewed=false`，进入待复核队列而不是直接作为终态。

为什么需要：在合规敏感的保险场景，**一条被误判的投诉，代价比一条被漏标的赞美好得多**。
这不是不信任模型，而是给低置信度的判断留一个出口。

**`humanLabel`（人工修正）**

人工复核后写入，`confidence` 置 1 表示终态。这些修正结果可以回流作为 few-shot 样本，
形成闭环。

**`topics`（JSON 字符串）**

存 JSON 数组，配合后端 `TOPIC_TAGS` 常量做校验。这是已知的技术债——
查询只能走 `contains`，数据量大时应改为关联表（README 中已标注）。

### 模型映射

| 原 | 新 | 变化 |
|---|---|---|
| `Keyword` | `Topic` | 加 `hitCount` / `autoGenerated` / `approved` |
| `Hotspot` | `Feedback` | 去社媒字段，加情感/主题/紧急度/置信度/复核 |
| `Notification` | `Alert` | 加 `urgency` / `handled` |

## 四、业务字典：整个分析层的骨架

新建 `server/src/constants.ts` 与 `client/src/constants.ts`（两份保持一致）。

**为什么单独抽出来**：主题标签体系同时被四处使用——

1. AI Prompt 的输出约束（模型只能从这里选）
2. 后端落库校验（`analyzeFeedback` 中过滤非法标签）
3. 前端筛选下拉
4. 归因报告的主题分布

如果不集中管理，加一个主题要改四个地方，必然漏。

**12 个主题标签的定法**：理赔时效、赔付金额争议、拒赔争议、核保与投保、客服响应、
服务态度、条款清晰度、销售误导、续保与退保、APP 与网站体验、价格与性价比、理赔资料繁琐。

数量控制在 12 个是有意的——标签太少区分度不够，太多模型容易选错、业务也看不过来。

## 五、AI 分析层：核心改造

这是整个项目技术含量最高的部分，也是最需要讲清楚设计理由的部分。

### 5.1 输出从"三元组"变成"六元组"

| 原输出 | 新输出 |
|--------|--------|
| `isReal`（真假） | `sentiment`（情感） |
| `relevance`（相关性 0-100） | `topics`（业务主题，数组） |
| `importance`（重要度） | `urgency`（紧急度，四级） |
| `summary`（摘要） | `aiSummary`（归因，不是摘要） |
| — | `urgencyReason`（定级理由） |
| — | `confidence`（置信度） |

**`summary` → `aiSummary` 的语义变化值得注意**：原版是"内容摘要"，
新版要求"一句话点出客户不满的**具体环节**"。这是从"它说了什么"到"哪出了问题"的转变，
也是业务价值所在。

### 5.2 五个关键 Prompt 设计决策

**① 主题从预设列表选，禁止自造**

```
2. topics：从【可选主题标签】中选择 1-3 个，**不要自造标签**
```

不加这条约束，模型会输出"理赔问题""效率低下"这类自由文本，
一段时间后标签数量爆炸，报表没法看。后端也做了二次校验（`TOPIC_TAGS.includes`），双保险。

**② 显式列出粤语负面表达**

```
【语言注意】
客户可能使用繁体中文、粤语口语或中英混排。以下均为强负面表达：
"唔賠""搵笨""搞咁耐""拖咗好耐""極不負責任""講一套做一套""no response""waste of time"
```

通用情感模型多在简体中文或英文语料上训练，对粤语口语识别率低。
显式列出是最低成本的领域适配手段。

**③ Few-shot 覆盖四种语言形态**

给了 3 条示例，分别是：粤语负面、英文拒赔升级（critical）、繁体正面。
覆盖典型场景，比单纯描述规则有效得多。

**④ `temperature = 0.1`**

标注任务要的是一致性，不是创造性。高温会导致同一条文本多次分析结果不同，
评测准确率也会剧烈波动。

**⑤ 置信度自评**

让模型自己输出 confidence。这不是让它"诚实"，而是给下游一条路由规则——
低置信度转人工。

### 5.3 归因报告：统计与归纳分离

`generateInsightReport()` 的设计：

```
统计部分（反馈量、评分均值、负面占比、主题分布）→ 代码计算
归纳部分（归因结论、改进建议）                  → LLM 生成
```

**为什么这么分**：计数是 LLM 的弱项，容易编造数字。这些指标必须可复现、可对账，
交给代码；而"为什么评分低""怎么改进"是语义任务，正是模型擅长的。
各用所长，而不是全丢给模型。

## 六、数据源：删除比新增更重要

### 6.1 删除整个爬虫层

删除 `twitter.ts`、`search.ts`、`chinaSearch.ts`、`test-sources.ts`。

理由：保险客户反馈来自**内部业务系统**，不是公开网络。
留着爬虫代码只会让接手的人困惑"这些是干嘛的"。

这是改造中最容易被忽略的一步——**做加法容易，做减法需要判断力**。

### 6.2 新增语料与导入

`services/feedbackSource.ts` 包含两部分：

**① 演示语料生成**：57 条覆盖 12 主题 × 3 情感 × 4 语言形态的香港保险场景文本。
每条语料自带人工标注（topic / sentiment），可直接作为评测集使用。

**② 文件导入解析**：支持 CSV / JSON。

生产接入点被隔离在 `insightRunner.ts` 的 `fetchNewFeedback()` 一个函数里——
换成业务系统接口时只需改这一处，这是有意为之的解耦。

## 七、服务层与调度

### 7.1 主流程（`jobs/insightRunner.ts`）

```
拉取激活主题词
  → 采集一批反馈
  → 主题词扩展（书面术语 → 客户口语）
  → 预匹配（未命中则跳过，节省 AI 调用）
  → AI 结构化标注
  → 落库 + 命中计数
  → 预警判定（action/critical 才告警）
  → 突增检测
```

**预匹配的意义**：先用扩展词做字符串匹配，未命中的不送 AI。
AI 调用是成本与延迟的主要来源，这一步能过滤掉大部分无关反馈。

### 7.2 主题突增检测

单条反馈看不出系统性问题——一条"理赔慢"是偶发，20 条"理赔慢"是流程出事了。

实现：统计 24 小时内各主题的负面反馈数，超过阈值（5）触发预警。
**带 12 小时静默期**，否则同一批数据会反复告警，导致告警疲劳。

### 7.3 降级设计

`isAIConfigured()` 判断 AI 是否真的可用。不可用时走规则兜底
（负面词表 + 评分判定），流程照常跑通。

**为什么需要**：保证开发、演示、测试不依赖外部服务的可用性。
一个没配 Key 就白屏的项目，交接成本极高。

注意这里有个细节——只判断"非空"是不够的，`.env.example` 里的占位 Key 也是非空，
会导致每次都发出必然失败的请求。所以额外排除了 `your_` 前缀。

## 八、前端

改造顺序：`api.ts`（类型契约）→ `socket.ts`（实时事件）→ `constants.ts`（字典）
→ `FilterSortBar.tsx` → `App.tsx`。

**先改 `api.ts` 的原因**：它定义了前后端契约。契约定了，页面怎么改都不会偏离。

`App.tsx` 拆成四个页面：

| 页面 | 作用 |
|------|------|
| 反馈洞察 | 概览指标 + 筛选 + 列表 |
| 主题词管理 | 增删改 + AI 扩展 + 确认启用 |
| 评分归因 | 主题分布 + AI 结论与建议 |
| AI 试算 | 单条文本即时分析，验证 Prompt 效果 |

**AI 试算页值得单独说**：它不落库，纯粹用来调 Prompt。
改完 Prompt 立刻粘几条文本看效果，迭代效率比跑批量高一个数量级。
这是给自己（和后来接手的人）留的调试入口。

## 九、验证：怎么确认没改坏

改造涉及 30+ 文件，必须有可复现的验证路径。四层：

| 层次 | 命令 | 验证什么 |
|------|------|---------|
| 类型 | `cd server && npx tsc --noEmit` | 类型正确性（Prisma 模型变更后尤其重要） |
| 单元测试 | `cd server && npm test` | 排序逻辑、兜底行为 |
| 构建 | `cd client && npm run build` | 前端可构建 |
| 端到端 | 启动服务 + 调用接口 | 数据库、路由、分析链路连通 |

**端到端冒烟是关键一环**。前面三层都过了，服务仍可能起不来（比如忘了 `prisma db push`）。
实际执行时确实通过冒烟发现了数据库未建表的问题。

### 评测集

`__tests__/aiRelevance.test.ts` 不只是测试，更是**Prompt 迭代的度量工具**。
12 条用例覆盖四种语言形态，输出三项准确率。

它的存在让"Prompt 调好了"这句话可以被证伪——这是工程与玄学的区别。

## 十、UI 风格改造

在功能完成后单独进行的一轮改造：深色科技风 → 浅色企业风。

**动因**：科技风（粒子背景、霓虹渐变）是开发者工具的语言，
不符合保险/金融行业"稳重、专业、可信"的审美。
演示给保险行业的人看，深色科技风可能是减分项。

**改动**：

| 项 | 改前 | 改后 |
|---|---|---|
| 布局 | 顶部 Tab | 左侧深色侧边栏 + 白色顶栏 |
| 配色 | 深色 + 蓝紫渐变 | 白底 + `#2563eb` 单色主色 |
| 列表 | 卡片流 | 数据表格（点击行展开详情） |
| 筛选 | 下拉胶囊 | 工具栏（搜索框 + 原生 select） |
| 动效 | framer-motion + 粒子光束 | 全部移除 |

**意外收益**：移除 framer-motion 后，JS 从 426 kB 降到 306 kB，
CSS 从 39.8 kB 降到 25.9 kB。动效库的体积成本比想象中高。

表格"点击行展开详情"的设计兼顾了两点：表格提供信息密度（管理系统该有的样子），
展开区容纳 AI 归因、定级理由、人工复核（信息量不丢失）。

## 附录 A：踩坑记录

改造过程中实际遇到并修复的问题，记录下来避免重复踩。

### A1. `tsconfig` 模块配置在 TS 5.9 下报错

```
error TS5110: Option 'module' must be set to 'NodeNext' when option 'moduleResolution' is set to 'NodeNext'.
```

原配置为 `module: ESNext` + `moduleResolution: NodeNext`，TS 5.9 起不再接受这个组合。
改为 `module: NodeNext`。项目本就是 ESM（`type: module`），import 已带 `.js` 后缀，改后无副作用。

### A2. Prisma 需要 `.env` 才能执行

`prisma.config.ts` 中使用 `env("DATABASE_URL")`，没有 `.env` 时连 `prisma generate` 都跑不了。
从 `.env.example` 复制一份即可。

### A3. JSON 解析导致隐式 any

```typescript
const parsed = JSON.parse(raw);        // any
const list = Array.isArray(parsed) ? parsed : parsed.data ?? [];  // 仍是 any
list.map(...).filter(item => ...)      // item 隐式 any，TS7006
```

修复：给 `parsed` 和 `list` 显式类型标注。教训是 `JSON.parse` 的返回值会污染整条调用链。

### A4. 占位 API Key 导致评测失真

测试里用 `!!process.env.OPENROUTER_API_KEY` 判断是否跑 AI 用例，
但 `.env` 里是占位符 `your_openrouter_api_key_here`，非空 → 判定为已配置 →
发出必然失败的请求 → 走兜底 → **准确率统计出来是 0**。

修复：测试侧改为 `API_KEY.startsWith('sk-or-v1-')`；
服务侧 `isAIConfigured()` 额外排除 `your_` 前缀。

**这个问题的隐蔽性在于**：测试"通过"了（有 fallback），但数字是假的。
如果没留意，很可能把 0% 或者虚假数字写进简历。

### A5. lucide-react 新版本图标重命名

`BarChart3`、`ShieldQuestion` 在 0.563 版本不可用。
排查方法：**优先使用原项目中已存在的图标**（那些是验证过能用的），
新引入的图标要确认。

### A6. 空测试文件导致 vitest 失败

把废弃测试文件清空为 `export {}` 后，vitest 报
`No test suite found in file`。要么删掉文件，要么保留一个占位用例。

### A7. PowerShell 中文路径乱码

命令行传中文路径会被按 GBK 解码导致乱码（`E:\ai 搴旂敤鎳傜帇\...`）。
规避方式：**用相对路径**（shell 已初始化在项目根目录），如 `cd server` 而非
`cd E:\ai 应用懂王\...\server`。同理，命令输出中避免中文字符。

## 附录 B：如果重做一次

诚实记录几个可以做得更好的地方：

1. **`topics` 不该用 JSON 字符串存**。查询只能走 `contains`，无法精确统计与索引。
   应该用 `FeedbackTopic` 关联表。当前设计是为了控制改造规模做的妥协，已在 README 中标注。

2. **语料量偏少**。57 条对于演示够用，但做评测样本量不足（12 条用例）。
   如果有条件，应该构造 200+ 条带人工标注的数据集，评测结果才更有说服力。

3. **前端拆组件可以更早**。最初把四个页面都写在 `App.tsx`（800+ 行），
   后来 UI 改造时才拆出 `Layout` / `FeedbackTable`。一开始就拆会更省事。

4. **缺少鉴权与多租户**。当前是单机原型，生产需要按部门隔离数据与预警路由。
   这一条在 README「生产落地需要补的部分」中列出了。
